04. TECHNOLOGY CHOICES AND SYSTEM BOUNDARIES
======================================================================

Use React through Next.js App Router with TypeScript strict mode. Next.js provides public server rendering, routes, metadata, image presentation, and the admin UI. Keep most public components server-rendered; use client components only where browser interaction is required.

Required frontend dependencies:
- Tailwind CSS for the design token system and responsive styling.
- Motion for a small number of restrained transitions.
- Accessible headless primitives or shadcn-style components for dialogs, menus, tabs, and administrative controls, restyled to this design.
- React Hook Form with Zod for client-side form feedback.
- TanStack Query for authenticated remote state and mutations.
- A maintained image-crop/focal-point interaction library if it meaningfully reduces implementation complexity.
- Vitest, React Testing Library, Playwright, and an accessibility test integration.

Required backend dependencies:
- FastAPI and Pydantic for request/response validation and OpenAPI.
- SQLAlchemy 2.x with the psycopg driver and PostgreSQL.
- Alembic for versioned schema migrations.
- A maintained Argon2id password hashing library.
- Pillow or an equivalent maintained raster decoder for verified image processing.
- A PDF parser to validate résumé uploads.
- pytest and HTTPX for service and API verification.

Use a synchronous SQLAlchemy service layer and ordinary synchronous FastAPI handlers for database-heavy operations unless the existing repository already has a consistent async design. Do not mix sync database calls into async handlers on the event loop. Use one database session per request; end transactions explicitly. Run image decoding in the appropriate worker/thread execution path, with strict resource limits.

Choose supported stable package versions at implementation time, verify their compatibility using official documentation, and pin the resolved versions. Commit the JavaScript and Python lockfiles. Select a supported Node LTS, supported Python release, and supported PostgreSQL major. Do not use floating "latest" container tags or copy old version numbers without checking them.

Use one public origin. A reverse proxy serves:
- /api/v1/* to FastAPI, preserving the path.
- All other application routes to Next.js.

Next server components call FastAPI with a private API_INTERNAL_URL. Browsers use relative /api/v1 paths. Configure an equivalent development proxy so cookie and CSRF behavior is exercised through the same origin. Never put database URLs, session secrets, storage credentials, SMTP passwords, or internal service URLs into NEXT_PUBLIC variables.

FastAPI is the sole authority for passwords, sessions, content validation, publishing, uploads, public media authorization, and contact persistence. Next.js must not create a competing authentication database or write directly to PostgreSQL.

Start with explicit no-store behavior for public content responses and public HTML. At this portfolio's scale, immediate consistency is more valuable than a complicated cache layer. Static fonts, CSS, JavaScript, and decorative assets can use fingerprinted immutable caching. A future public-content cache requires a tested invalidation and media-removal policy.

PostgreSQL is the source of truth. Browser state is for interaction and unsaved edits, never the authoritative CMS store. No required feature may depend on mock JSON responses after implementation.

5. Optional authored decisions, challenges, and reflections.
6. Optional gallery with captions and meaningful alt text.
7. Verified live and repository links.
8. Navigation to another current published project and a contact link.

Do not generate long imaginary case studies to make the design look populated. Both initial pages can be concise, complete, and attractive with the supported facts in section 03. An absent optional section should leave no empty heading or placeholder paragraph on the public page. The admin can show instructional placeholders inside empty fields.

The gallery starts with no images. Once populated, display responsive images with explicit dimensions. A lightbox is optional; if implemented, it must support keyboard navigation, Escape, focus restoration, clear captions, and a visible close button. Do not autoplay slides. Every image remains understandable outside the lightbox.

Project routes use stable item IDs internally and slugs for public URLs. A missing or hidden project returns a true 404. A previously published slug may redirect only to the current visible project that has the same stable ID. A withdrawn project is removed from the application's redirects, sitemap, public API, and any application-owned search index. Its media becomes unavailable only when no item in the current public projection still references it. The application cannot recall downloaded bytes or promise immediate removal from external search-engine caches.

Do not place a fake repository link pointing at the owner's GitHub profile under a "Source code" label. A general GitHub profile link belongs in the site's social links. Demo links may open a new tab with an appropriate rel value and accessible context; be consistent across both projects.

Use metadata from the actual project: title, concise description, canonical current URL, and a permitted social image. If no screenshot exists, a designed title/initials social card is acceptable when it is presented as site artwork rather than evidence of the project interface.

09. PHOTO, RÉSUMÉ, AND PROJECT MEDIA EXPERIENCE

PORTRAIT EMPTY STATE
The missing photograph is not a broken asset. Render a sage panel with large teal serif initials "GK," a fine copper detail, and "Portrait coming soon." Give the component reserved 4:5 dimensions. Decorative lettering should not produce a verbose screen-reader announcement; the accessible description can identify the portrait placeholder once.

PORTRAIT UPLOAD WORKFLOW
1. Select a JPEG, PNG, or WebP within the displayed 8 MiB limit.
2. Show upload progress or an indeterminate processing state if exact progress is unavailable.
3. The backend validates and decodes the file, applies orientation, strips metadata, and creates safe variants.
4. The editor shows a 4:5 crop preview and a separate mobile preview.
5. The owner adjusts horizontal position, vertical position, and zoom, using either pointer controls or equivalent labeled numeric/slider controls.
6. Applying the crop creates a new immutable derived media asset. It does not replace bytes at an existing public URL.
7. The owner supplies alt text, saves the draft, previews, and publishes.

Store crop bounds normalized to the decoded source image: x, y, width, height in [0,1], with positive dimensions and no overflow. Validate the 4:5 ratio in source-pixel space, allowing only documented pixel-rounding tolerance. Do not compare normalized width/height directly as if every source were square. Reset returns to a centered valid crop. A very small image can be accepted with a quality warning, but do not upscale it excessively or claim it is high resolution.

Both desktop and mobile use the saved framing. Remove portrait switches the draft back to the GK placeholder. Cancel retains the existing selection. A failed upload, crop, or save keeps the previously valid asset and provides a retry. The published portrait changes only after a successful publish transaction.

PROJECT MEDIA
Support one optional cover and an ordered gallery of up to 12 images per project. Each image reference has meaningful alt text and an optional caption. Provide keyboard-accessible move-up/move-down controls as well as optional drag reordering. A cover does not need to be duplicated in the gallery.

RÉSUMÉ
Import the supplied Gagandeep_kaur_resume.pdf through the same validated media pipeline when the file is accessible. Make the seed/import command accept an explicit résumé path; do not commit absolute paths from this workspace. If the attachment is unavailable to the implementation environment, create a working upload control and hide the public download until an actual PDF is supplied. Do not fabricate a replacement résumé or expose an empty PDF.

Résumé replacement is a draft edit. The existing public PDF remains available until publication. Use a stable /api/v1/resume route that resolves the current release and serves the active file with a safe filename such as Gagandeep_Kaur_Resume.pdf. Return 404 when no public résumé exists. Display file type and size where useful.

MEDIA LIBRARY UI
Show a thumbnail or PDF icon, original display name, upload date, dimensions/type, size, processing status, and usage. Allow filtering by image/PDF and searching display names. A delete action displays what currently references the asset and is blocked while a retained draft, release, or derived child requires it. Distinguish removing an image from a page from permanently deleting stored bytes.

Disable accidental duplicate saves while a request is pending, but allow canceling navigation dialogs.

Warn before browser/tab navigation when unsaved changes exist. Do not persist sensitive content or session tokens in localStorage. Use one versioned JSON document for the small portfolio content model, validated by strict Pydantic schemas. Store it in PostgreSQL JSONB, but do not accept arbitrary JSON. NarrativeBlock: stable id; kind in paragraph|bullet_list; optional heading; text or items. No raw HTML blocks.

PROFILE
full_name (1–100), role_label (1–120), hero_eyebrow (0–160), intro (1–400), biography (0–2000), institution_context (0–180), email (validated address), phone_display and phone_e164 (nullable), github_url and linkedin_url (nullable approved http/https URLs), portrait (MediaRef|null), resume_asset_id (UUID|null). PROJECT
ContentItem plus slug, title, category, summary, overview, feature_bullets, technologies, narrative_blocks, live_url, repository_url, cover, gallery, seo_title, seo_description.

Empty slugs, summaries, overviews, and technology lists are permitted while editing. Publication requires nonempty valid values for every visible project. Optional URLs are null when absent. SEO title is at most 70 characters and description at most 180 as editorial limits, not search-engine guarantees.

EXPERIENCE

LEADERSHIP
ContentItem plus organization, role, start, end, is_current, description, bullets, metrics. Up to four scoped metrics per item. The IEEE Day 2025 callout may be a recognition entry referenced by settings; do not create inconsistent copies with different numbers.

EDUCATION
ContentItem plus qualification, institution, start_year nullable, completion_year nullable, is_current, result_label, result_value, result_note. SKILLS

RECOGNITION

SETTINGS
site_url, default_seo_title, default_seo_description, section_labels/intros keyed by the fixed home sections, visible_sections, featured_project_ids, featured_recognition_id nullable, show_phone=false, show_resume=true when valid PDF exists, availability_enabled=false, availability_text nullable. Security settings, retention duration, rate limits, SMTP, and deployment secrets are environment/operator configuration, not editable arbitrary strings in the public CMS.

LIMITS AND PUBLICATION RULES
- Entire draft JSON request: maximum 256 KiB before parsing.
- Up to 30 projects and 50 items in each other collection; reject excess with field errors.
- No unknown schema keys. Normalize whitespace without corrupting multiline text.
- Only safe http/https external URLs; reject javascript/data/file schemes, credentials in URLs, and malformed addresses. Never fetch arbitrary owner-entered URLs server-side.

- Public projection filters hidden items/sections and removes internal notes, original filenames, storage keys, admin metadata, invisible phone values, and draft-only fields.
- A content schema migration must explicitly upgrade old drafts/releases or retain a compatible reader. Do not let a new application version make historical releases unreadable.

12. POSTGRESQL SCHEMA AND DATA INTEGRITY
======================================================================

Use Alembic migrations, UUID identifiers, TIMESTAMPTZ timestamps in UTC, explicit foreign keys, and indexes that support actual queries. Keep one writable content document. Do not introduce independently writable project/education tables that can diverge from it.

site_drafts
- id SMALLINT primary key, constrained to 1.
- schema_version INTEGER not null.
- content JSONB not null, validated against SiteContent.
- revision BIGINT not null, positive, incremented on each successful replacement or restore.
- updated_by UUID nullable foreign key to admin_users; null for initial operator seed.
- updated_at TIMESTAMPTZ not null.

site_releases
- id UUID primary key.
- revision BIGINT unique not null, assigned by a database sequence; gaps are allowed.
- schema_version INTEGER not null.
- source_content JSONB not null: private full validated content used for restoration.
- public_content JSONB not null: separately derived public projection.
- content_hash TEXT not null: canonical source-content digest.
- source_draft_revision BIGINT not null.
- publish_idempotency_key UUID unique not null.
- publish_request_hash TEXT not null.
- created_by UUID nullable foreign key to admin_users.
- created_at TIMESTAMPTZ not null.
Releases are immutable through application APIs. Public endpoints select public_content explicitly; never serialize the release ORM object or source_content. The existence of a private historical source snapshot does not grant public access to its hidden fields or media.

site_state
- id SMALLINT primary key, constrained to 1.
- live_release_id UUID nullable foreign key to site_releases, deletion restricted.
- updated_at TIMESTAMPTZ not null.
Before initialization there may be no live release; treat this as a configured maintenance/unpublished state, not a successful empty portfolio.

admin_users
- id UUID primary key; normalized_email TEXT unique not null.
- password_hash TEXT not null; is_active BOOLEAN not null.
- created_at, updated_at, password_changed_at TIMESTAMPTZ.
Enforce the one-owner product rule in the bootstrap service. Do not expose a public account-creation endpoint.

admin_sessions
- id UUID primary key; admin_user_id foreign key not null.
- token_digest TEXT unique not null; csrf_token_digest TEXT not null.
- created_at, expires_at, last_activity_at TIMESTAMPTZ not null.
- revoked_at TIMESTAMPTZ nullable.
Index active lookup/expiry. Never store the bearer session token or raw password.

media_assets
- id UUID primary key; kind image|pdf; status processing|ready|deleted|failed.
- verified_mime TEXT; sanitized_source_key TEXT private; variants JSONB private.
- source_width/source_height INTEGER nullable; page_count INTEGER nullable.
- byte_size BIGINT, sha256 TEXT, original_display_name TEXT.
- parent_asset_id UUID nullable foreign key to media_assets, deletion restricted.
- crop JSONB nullable, using the validated normalized crop contract.
- created_by UUID nullable; created_at, deleted_at TIMESTAMPTZ.
Variants record actual width, height, MIME, byte count, hash, and private key. A public DTO returns approved same-origin variant URLs and dimensions, never private keys or original upload paths. Asset bytes and variant identities are immutable after ready.

contact_submissions
- id UUID primary key; idempotency_key UUID unique not null; request_hash TEXT not null.
- name, email, subject, message TEXT, validated and nullable only after deletion/retention scrubbing. Normalize an omitted subject to an empty string while the submission is active.
- is_read BOOLEAN default false; is_archived BOOLEAN default false.
- notification_status enum not_configured|pending|processing|sent|failed.
- created_at, updated_at TIMESTAMPTZ; deleted_at nullable; receipt_expires_at TIMESTAMPTZ.
- notification_attempted_at nullable; sanitized notification_error_code nullable.
Index created_at and the unread/unarchived list filter. Messages are plain text. Deletion scrubs sender/content fields and retains only the receipt/key/hash until the short retry window expires; cleanup then deletes the tombstone. A replay during that window returns the same receipt without recreating the message.

rate_limit_buckets
- scope TEXT; key_digest TEXT; window_start TIMESTAMPTZ as composite unique key.
- count INTEGER nonnegative; expires_at TIMESTAMPTZ.
Use atomic inserts/updates or locked rows, deterministic lock order, and cleanup of expired buckets. An in-process dictionary is not sufficient across API workers.

slug_redirects
- old_slug TEXT primary key; project_id UUID not null; created_release_id foreign key.
The project ID refers to a stable UUID inside content snapshots, so enforce referential rules in the publishing service. Do not pretend a conventional SQL foreign key can point inside arbitrary JSONB.

admin_audit_events
- id UUID primary key; actor_id nullable foreign key; operation TEXT; target_type/target_id nullable.
- request_id UUID; metadata JSONB restricted to safe identifiers/status; created_at.
Record login security events, publish, restore, media deletion, and contact deletion without storing secrets or full draft/message bodies in the audit table.

All JSON asset references are checked through one typed reference-extraction function used by save, publish, restore, deletion, and backup verification. A string search through serialized JSON is not a reliable reference check. Transactions, not UI state, enforce uniqueness and ownership.

======================================================================
14. DRAFTS, ATOMIC PUBLISHING, HISTORY, AND SLUG REDIRECTS
======================================================================

DRAFT SAVE TRANSACTION
Acquire the singleton draft row FOR UPDATE. Check the strong If-Match ETag; reject weak, wildcard, malformed, or stale values. Validate the complete document, referenced asset readiness, identifiers, and bounds. Replace content, increment revision exactly once, update actor/time, and commit. Failed validation or a failed transaction leaves the prior content/revision intact. A save has no effect on the live pointer.

PUBLISH TRANSACTION
Use fixed lock order: draft row, site_state row, then media rows in a stable order. Under the lock, check whether the idempotency key has already completed. If it has the same canonical request hash, return the original receipt without changing the pointer; if the payload differs, return 409 IDEMPOTENCY_CONFLICT.

For a new operation:
1. Verify expected_draft_revision and expected_live_release_id.
2. Validate the saved draft for publication, including visible content and ready assets.
3. Resolve the prior release and validate slug/alias ownership by project UUID.
4. Derive one sanitized public projection.
5. Insert one immutable release with private source_content and public_content.
6. Record aliases for retained visible projects whose slugs changed.
7. Update live_release_id and the audit record.
8. Commit all changes together.

Return a 409 publication conflict when either precondition changed. The UI reloads the current status and asks the owner to review the current content; it never silently publishes a revision the owner did not review. After any replay receipt, refetch current state: a successful historical receipt does not mean that release is still live.

Read public content by joining the live pointer to one immutable snapshot. A home page fetches the aggregate once, then uses that object for all sections and metadata. Do not issue independent per-section queries that can combine two different releases during publication. Use request-scoped memoization if needed, not a persistent public-content cache.

RESTORE
Restore copies a release's full private source_content into a newly saved draft revision, preserving stable IDs and hidden items from that historical source. It leaves the live release unchanged. Validate media and schema compatibility. Show the owner what will change, especially if the current draft has edits. Require the current draft ETag. Publishing the restored draft creates a new release, preserving history.

SLUG RULES
A slug belongs to a stable project UUID. When a visible retained project changes slug, keep the old slug as an alias to that UUID. Resolve every alias against the current public snapshot, avoiding redirect chains. If the project is withdrawn, every alias returns 404. Reject reusing another project's retained alias. An alias that belongs to the same project can become its current canonical slug again.

A project hidden only in the draft is still live until publication. A deleted draft item behaves the same way. Make that distinction clear in the editor. Never delete historical release rows as a side effect of hiding a project.

Release retention is an operator maintenance task with a dry-run report. Do not delete the current release or invalidate restorable media silently. Preserve all releases by default for this small application; document how to prune old releases and then reclaim unreferenced media intentionally.

15. AUTHENTICATION, SESSIONS, AND AUTHORIZATION
======================================================================

Bootstrap the owner with a CLI that prompts securely for email/password. Do not seed a default password, accept a password as a visible shell argument, or put it in a README. Provide a separate password-reset CLI and session-revocation command for the operator.

Use a maintained Argon2id library with documented parameters. Accept long passphrases without silent truncation. Require a minimum of 12 characters and a reasonable maximum such as 256 characters; enforce length before expensive hashing. Do not add arbitrary forced symbol rules. Login failures use one generic response rather than disclosing whether an account exists.

Generate at least 32 cryptographically random bytes for the opaque session token. Store a digest only. Production cookie: __Host-portfolio_session; Secure; HttpOnly; SameSite=Lax; Path=/; no Domain. In explicit HTTP development mode use a different cookie name and visibly documented relaxed Secure setting. Production startup must refuse an insecure session-cookie configuration.

Default session policy: 12-hour absolute lifetime and one-hour inactivity limit, enforced server-side. Rotate the token on login and password change. Logout revokes it immediately in PostgreSQL. Expired or revoked sessions cannot read draft media, inbox, history, or content even if the browser retains a cookie.

Derive a session-bound CSRF token using HMAC-SHA-256 with the server-only CSRF_SECRET over a purpose-separated encoding of the presented opaque session token. Store its digest with the session and return the derived token through the authenticated login/session response. This lets the server reproduce it for GET /admin/auth/session without storing a plaintext bearer secret. Keep the derived CSRF token in frontend memory; never expose CSRF_SECRET itself. Compare submitted token digests safely. Rotating CSRF_SECRET requires revoking existing sessions unless explicit key versioning is implemented.

Authenticated unsafe requests require X-CSRF-Token plus exact allowed Origin. A Referer fallback, if supported, must validate scheme, host, and port against the configured origin; do not use prefix matching. Login also requires same-origin JSON requests. Missing/foreign Origin is rejected unless a documented trusted non-browser operator route uses a separate explicit mechanism.

Use same-origin browser routing. Do not use wildcard credentialed CORS. Trust forwarded host/protocol/IP headers only from configured proxies. Treat Host and returnTo inputs as untrusted. A login redirect destination must be a validated local /admin route; reject protocol-relative and encoded external destinations.

Rate-limit login using PostgreSQL counters across workers, for example five failed attempts per 15 minutes for an IP/email pair and a broader per-source ceiling. Successful authentication can clear the narrow failure bucket. Avoid permanent account lockouts that an attacker can trigger indefinitely.

Enforce authorization in every FastAPI admin handler/service dependency. Frontend route guards improve navigation but do not replace backend checks. Never place session tokens in URLs, localStorage, analytics events, or public Next props. Add CSP compatible with the actual Next application, frame-ancestors protection, nosniff, and a suitable Referrer-Policy. Verify the deployed CSP does not break legitimate framework scripts; do not use an untested policy copied from another app.

16. MEDIA PROCESSING, STORAGE, AND ACCESS CONTROL
======================================================================

Enforce body limits at the reverse proxy and while streaming in the API. Image maximum: 8 MiB. Résumé PDF maximum: 10 MiB. Configure proxy multipart overhead slightly above these per-file limits, while the API enforces the exact file limit. Only the authenticated owner uploads.

For images, accept JPEG/PNG/WebP by verified decoder result, not extension or submitted MIME. Reject SVG, HTML, executables, animated files, invalid images, and decoded images above a documented cap such as 24 megapixels. Apply orientation, re-encode, strip EXIF/GPS and unnecessary metadata, and generate thumbnail/card/full variants with bounded dimensions. Never serve raw original uploads. Preserve aspect ratio; do not upscale beyond the decoded source merely to meet a target size.

For portrait derivatives, enforce exact 4:5 output dimensions and preserve the original sanitized source privately for future recropping. The crop endpoint uses the contract from section 09. Finalizing a derived record acquires the draft lock then parent asset lock and rechecks parent readiness, preventing a concurrent deletion race. A crop returns a new asset ID. It does not attach itself to the draft or alter an existing published asset.

For PDFs, verify the signature and parse a bounded unencrypted document with at most 20 pages. Reject malformed structure, JavaScript, launch actions, embedded attachments, and unsupported encryption. Do not claim that parsing constitutes antivirus certification. Use application/pdf, nosniff, and a sanitized attachment filename. Keep PDF validation errors useful without exposing parser internals.

Storage adapter interface: write_private, read_private, stat, delete, and health_check. Implement a persistent local filesystem adapter; provide an S3-compatible private-bucket adapter or a tested extension point with explicit deployment limitations. Do not advertise S3 as implemented if it is only a stub. Both adapters use random server-created keys, never user-controlled paths. The local media root is outside the web root and mounted as a persistent volume.

Process media outside long database transactions. Write temporary private files, decode/validate, generate variants, then register a ready asset. A processing failure removes temporary bytes and leaves no usable public record. A crash can leave private orphans; provide a maintenance command that reports and cleans them after a safe age threshold. Missing storage during a read returns a controlled error and logs a request ID, not an arbitrary local path.

Public asset authorization is derived from the current public_content snapshot at request time. A historical release or draft reference alone is insufficient. Allow only the requested approved variant for the referenced kind. The owner endpoint may access retained ready assets for editing and history. Public requests for private, missing, deleted, or hidden-only assets use uniform 404 responses.

Serve generated variants directly with no-store. Bypass or block Next's image optimizer for managed media; do not create a second publicly cached /_next/image route around access control. Do not mount the media volume as a public nginx directory or expose permanent public bucket URLs. An asset removal cannot recall bytes already downloaded; document this practical limit without claiming absolute revocation.

If publication races an old page's image request, the old asset may become unavailable. The image component should fall back gracefully and, at most once, refresh the current release; it must not bypass authorization to recover old bytes.

For deletion, acquire the singleton draft lock first, then the asset lock. Check typed references in the current draft, every retained source/public release, and derived children. Any reference returns 409 MEDIA_IN_USE with an owner-safe usage summary. Draft saves, publication, restoration, and crop finalization use compatible lock ordering, preventing a new attachment from racing deletion.

For an unused asset, mark deleted transactionally before removing bytes. If physical removal fails, access stays denied and cleanup retries later. Do not delete a parent while a retained derivative depends on it. Replacing a visible image changes a reference in a later release; it never mutates old asset bytes.

17. CONTACT DELIVERY, INBOX, IDEMPOTENCY, AND ABUSE CONTROLS
======================================================================

CONTACT BODY
{
  "name": "A prospective collaborator",
  "email": "sender@example.com",
  "subject": "Project enquiry",
  "message": "A plain-text message describing the opportunity.",
  "website": ""
}

website is an optional honeypot omitted from keyboard/screen-reader navigation and clearly separated from legitimate fields. It is only an additional spam signal. A filled honeypot can receive a generic rejection; do not fabricate a persisted-success receipt. No public file attachments are supported.

Limits: name 1–100 characters, validated email at most 254, optional subject at most 150, message 10–5000, entire JSON body 16 KiB. Normalize an absent subject to an empty string before storage and canonical hashing. Trim appropriate surrounding whitespace, preserve meaningful newlines, and render content as escaped text. Reject unsupported fields and control characters unsafe for processing. Do not demand a phone number.

The client generates one UUID idempotency key for one intended submission. Once a request is sent, keep its exact normalized payload/key through timeouts and retry. If the user deliberately changes the message after an ambiguous result, explain that retrying the original can determine whether it was received; do not silently reuse the old key for changed content.

TRANSACTION
1. Validate JSON, same-origin policy, lengths, and anti-abuse signals.
2. Compute a canonical request hash over validated message fields, excluding transient client UI metadata.
3. Acquire rate-limit bucket locks in deterministic order, including the site-wide bucket.
4. Check for the idempotency receipt under the serialized transaction path.
5. If the same key/hash exists, return its receipt without charging counters or creating another notification. A different hash returns 409.
6. For a new key, enforce limits, insert the message, and update counters in one transaction.
7. Commit before returning 201.

The unique key is a final database safeguard. Handle a concurrent unique conflict by rolling back the failed transaction, then reading the committed record in a fresh transaction and comparing its hash; never continue querying through an aborted PostgreSQL transaction or turn an expected retry into a generic 500. If the database is unavailable or commit fails, return 503, preserve the form/key, and do not show success.

Suggested configurable defaults: five new submissions per source-IP bucket per 15 minutes and a site-wide ceiling of 100 new messages per hour. Use an HMAC-derived source identifier with a server-only secret, not raw IP addresses in permanent message rows. Trust IP headers only from configured proxies. Expire rate-limit buckets within a short operational window and clean them through the maintenance command. Return 429 with Retry-After; a valid completed retry should not consume another quota slot.

MESSAGE RETENTION AND DELETION
Document a default 180-day retention period for contact content, configurable by the operator. Implement a dry-run and actual cleanup command, and provide a scheduled invocation example. The /privacy notice must reflect the configured period and contact purpose; do not claim the cleanup runs automatically unless the deployment actually schedules it.

Owner deletion or retention expiry scrubs sender/message data. Retain only the receipt UUID, idempotency key, hash, and expiry metadata for a 24-hour retry/tombstone window after deletion, then remove the tombstone. Deduplication is guaranteed only while the original receipt or tombstone is retained; after cleanup, an old UUID cannot be recognized. The client must not offer indefinite automatic retries. The public response does not reveal whether the owner read or deleted a message. Authenticated lists exclude deleted content. Backups have a separately documented retention period; deletion from the live database does not magically erase existing backups.

OPTIONAL EMAIL NOTIFICATION
The database inbox works with no SMTP configuration. If credentials are supplied, send a bounded best-effort notification after commit. Claim/record the attempt so duplicate client retries do not start another attempt. Use a configured fixed From and a validated Reply-To; never concatenate untrusted email headers. Record not_configured, pending, processing, sent, or failed accurately.

A web-process background task is not guaranteed durable delivery. A process crash may interrupt notification; show the status honestly in the inbox and document it. Notification failure cannot roll back the received message. Do not promise exactly-once email, automatically resend indefinitely, or tell the visitor that an email reached the owner.

INBOX BEHAVIOR
Read/unread and archive/restore persist on the server and survive refresh. Display sender/email safely, render multiline message text without HTML execution, paginate long lists, and show useful empty states. Reply opens the owner's mail client with a safely encoded recipient and subject. The application does not silently send an answer.

18. FRONTEND STATE, RENDERING, AND FAILURE HANDLING
======================================================================

PUBLIC RENDERING
Server-render the published home and project content. Fetch one release per page render with no-store and share it through that render's components/metadata. Do not ship all CMS editing code to public routes. Keep JavaScript islands small: mobile navigation, active chapter tracking, contact form, optional gallery controls, and progressive motion.

A client-side error must not blank out the biography and project links already rendered by the server. Reserve media dimensions. Prioritize the hero portrait only when present; lazy-load below-fold media. Use an ordinary picture/img with approved variants or a framework image component explicitly configured to avoid managed-media optimization/caching.

Do not fall back to stale hard-coded seed content when the API is down; it could resurrect withdrawn information. Render a useful retryable service-unavailable page with a 503 status where supported, and log the correlation ID. A missing project is a 404; an unavailable database is not evidence that a project does not exist.

ADMIN STATE
Use a DraftProvider for current document, last-saved baseline, revision, dirty sections, save status, and server field errors. TanStack Query owns server request state; it must not silently replace unsaved edits after background refetch. When fresh remote data arrives and local edits exist, show a conflict/reload decision.

Mutations:
- Save: complete document plus If-Match; update revision only after accepted response.
- Publish: saved revision only; require saving or explicitly discarding unsaved local changes first.
- Restore: replace current draft only after a confirmation that explains the effect.
- Upload/crop: return ready media metadata; attaching to content is a separate draft edit.
- Inbox status: optimistic feedback is permissible only with rollback on failure; confirmation of deletion follows server success.

Keep authentication state in cookies and CSRF token in memory. A protected-route 401 leads to a sign-in screen or reauthentication dialog. Preserve unsaved in-memory edits if the page can remain open. Do not repeatedly retry unauthorized mutations or lose the user's form because a background session request failed.

FIELD AND PAGE STATES
Every remote interaction has idle/loading/success/empty/error where relevant. Use skeletons only for actually pending content. Form errors appear beside their fields and in an accessible summary; focus the first invalid field after a rejected submission. Success notifications use a polite live region. Network errors retain inputs and explain the next action.

Use a shared API client for JSON errors, request IDs, credentials, CSRF headers, and bounded timeouts. Do not automatically retry unsafe mutations with a new key. Only retry a known idempotent operation using its original key and payload. Treat AbortError from user cancellation differently from server failure.

DRAFT-ISOLATION
Save a unique draft-only string. It appears in authenticated preview but not anonymous HTML, JSON, metadata, sitemap, error payloads, or public media. Anonymous requests cannot read inbox, release source snapshots, or preview bytes. Public DTOs exclude source_content and hidden contact data.

STALE-EDIT
Two clients load revision N. The first saves N+1. The second receives 412 when saving with N; the first content remains intact. Missing If-Match returns 428. Stale publication preconditions return 409. The frontend provides a usable conflict state rather than overwriting data.

ATOMIC-PUBLISH
Hold a publication transaction and verify public readers see the complete prior release. After commit, they see the complete new release. Inject a failure before pointer update and assert rollback. Retry the same publish key and assert one release; reuse it with a different body and assert 409. A replay of an old successful publish never moves the live pointer backward.

RESTORE-AND-SLUGS
Restore an older private source snapshot into a new draft while leaving live unchanged. Verify hidden items survive that restoration. Rename a retained project's slug; old URL redirects to its current slug. Hide and publish the project; canonical and aliases return 404. Reject alias reuse by another UUID.

SESSION-CSRF
Verify token rotation, hash-only session storage, expiry, inactivity, logout, password change, and operator reset. Through HTTPS, assert Secure/HttpOnly/host-only/SameSite cookie behavior. Foreign Origin, missing CSRF, and unsafe returnTo values fail without mutation. No session token appears in localStorage, public props, logs, or bundles.

MEDIA-VALIDATION-AND-CROP
Test valid raster formats, MIME spoofing, oversized bytes, excessive decoded pixels, SVG/executable rejection, metadata stripping, invalid PDFs, and a real PDF download. Test normalized crop bounds and source-pixel aspect ratio, immutable new IDs, correct 4:5 variants, and parent-deletion protection.

MEDIA-PUBLICATION-AND-DELETION
A replacement in draft preserves the old public image and keeps the replacement private. Publishing switches access according to current live references. An asset still used elsewhere remains public; an asset with no current public reference returns 404 on GET and HEAD, including optimizer/proxy bypass attempts. Race deletion against draft attachment and assert no dangling reference. Test logical deletion with storage deletion failure.

CONTACT-RETRY
Commit a message, simulate loss of its HTTP response, and retry the same key/body. Assert one stored message and the same receipt. Concurrent identical requests behave the same. A changed body with the same key returns 409. Database failure does not show success. SMTP failure does not lose the message. Deletion during the retained receipt window does not recreate the content on retry.

RATE-LIMIT-CONCURRENCY
Send competing requests near bucket boundaries through more than one API worker. Assert transactional ceilings and correct Retry-After. Valid completed retries do not consume new-message quotas. Verify untrusted forwarded IP headers do not bypass limits.

SEED-MIGRATION-PERSISTENCE

Test a supported migration against existing content and contacts. Verify incompatible content schema versions fail clearly rather than corrupting data.

RESPONSIVE-ACCESSIBLE

23. DEPLOYMENT, MONITORING, BACKUPS, AND OPERATIONAL OWNERSHIP
======================================================================

REFERENCE TOPOLOGY
Use one host or equivalent services running nginx, Next.js, FastAPI, and PostgreSQL. Only the proxy exposes public application ports. PostgreSQL and API stay on the private service network. Use a named PostgreSQL volume and a separate persistent media volume, or the explicitly implemented private object-storage adapter. Do not deploy uploaded files onto an ephemeral filesystem.

Build production images with pinned dependencies and unprivileged app processes. Configure request sizes, timeouts, trusted proxies, graceful shutdown, and TLS. Startup order is database readiness, one explicit migration step, then application services. Do not let every API worker run migrations independently on boot.
